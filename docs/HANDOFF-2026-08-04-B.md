## 1. v3.9.13 发了什么

### 真实缺陷:caller 分片反噬 issue #37

`getApiKey` 的候选排序把 in-flight 最少的排前面,好让并发突发散开(#37)。末尾的 caller
分片本意是"在同等好的账号之间让每个 caller 确定性地偏好自己那一格",但门槛只判
`candidates[0]` 与 `[1]` 打平,却按 `hash % candidates.length` 在**整个数组**上取下标 ——
于是能提拔一个与谁都不平的账号,**包括在场最差的那个**。

并发突发下正是如此:正在服务的账号按 in-flight 排到最后,队首两个空闲账号打平、门槛放行,
交换把最忙的拉回 `[0]`。实测 pool=8:某 callerKey 连续 8 次选中同一账号,七个同伴 in-flight
全是 0。**一直看不见,因为结果完全由 `sha256(callerKey) % pool` 决定**,而钉这条行为的测试
用的 callerKey 恰好 hash 到最好的那一档。8 个真实形态里只有 2 个真的散开全池。

修法:置换限制在真正与 `candidates[0]` 打平的前缀内。**判据必须镜像排序的每一项** —— 第一版
漏了 `recentTroubleScore`(排序第二优先键),既能提拔被降级的账号,又因该项优先级高而让扫描
提前停止、**分片不足**。

### 新开关 `WINDSURFAPI_STRICT_USAGE_TOTAL`(默认关)

恢复 OpenAI 的 `total_tokens == prompt + completion`。默认关,因为两种失效不对称:恒等式被破
对绝大多数消费者只是观感;而把 cache_write 从 total 拿掉会**少报真实开销**。

**难点不是加开关,是成本统计读的是同一个对象。** 天真地加会让运维一旦选择合规、自己的账单
当场少报。所以拆开两个职责:`total_tokens` 只管线上契约,成本统计取
`max(total, prompt + completion + cache_creation_input_tokens)`。三个 usage builder 全覆盖。

### 工具化 + 两条积压的结论

`npm run mutate`(见 §3)、可选 git hooks、以及两条 sticky 积压的答案:
`clearCallerBindings` **没有正确的触发点**(断连是主动错误的触发点);RPM 满即清绑定的
**显然修法是净负面**(保留绑定会散射,4/3 个冷账号 vs 清绑定的 2)已 revert 并留测试钉住。

## 3. 本轮新增的两个工具

### `npm run mutate -- test/mutations/<spec>.json`

突变验证从手搓循环变成脚本。三条**拒绝启动**的前置检查,每条对应一次真实事故:

| 拒绝条件 | 事故 |
|---|---|
| 工作树脏 | 循环自己的 `git checkout HEAD --` 会连未提交的修复一起还原,之后每次突变测的是"修复缺失"而不是"突变生效" —— 而那个失败**看起来正是突变被抓到**,所以读起来像成功 |
| baseline 不绿 / 条数不符 | 假 SURVIVED。本轮它两次抓到我自己的陈旧 spec |
| anchor 匹配次数 ≠ 1 | 匹配不上的 `replace` 是静默 no-op |

另外它会在突变后核对**测试条数**:条数变了**且什么都没失败**才中止 —— 那个 `&&` 是承重的,
少了它会在突变被真正抓到时误杀整轮(本轮真踩过)。

`expectCaught: false` 是**一等公民**,不是待修标记。"这条守不住"本身是结论。

### `.githooks/`(opt-in)

`pre-commit` 拒绝在 master 上写 commit;`post-commit` 对 `cherry-pick` / `revert` 事后警告。
**作用范围有九条断言钉住**(`githooks-scope.test.js`),因为那张表在同一轮里与实际行为偏离过
两次:

```
git commit / --amend        拦
git merge --ff-only         放行(不产生 commit,发版流程不受影响)
cherry-pick / revert        pre-commit 拦不住;由 post-commit 事后警告
冲突的 merge / rebase        拦,且给的是那个状态下真能执行的命令
未 opt-in                    完全不生效
```

## 5. 本轮学到的,按"最容易再犯"排序

台账第九、十轮有完整版。这里只列会直接害到下一个人的几条。

### 5.1 修复本身要过一遍复核

对抗复核六个 lens 攻本轮全部改动,**没有一条重大发现指向老代码 —— 全是这一轮新造的**。而每
一步都跑过突变验证。随后把裁决改窄成"审那六个修复本身",六条里**三条正中**。

一批修复是这一轮**唯一没人看过**的代码,而它们是在已经发现问题的紧张状态下写的。

### 5.2 一个守卫按一次复现写出来,就只对那一次复现正确

最清楚的例子:我按"截断"这一种复现写了"测试条数必须一致",然后无条件套用,于是在"真的被抓到
但条数也变了"的场景里把整轮杀掉。

**动作**:写下一个守卫后,问"**除了我复现的那一种,还有哪些情况会命中这个条件**",逐一给出
处置。答不出说明守卫没写完。

### 5.3 没看到信号,先问探针坏没坏

我给 post-commit 加了无条件 `echo`、跑 revert、没看到输出,就断言"git 对 revert 根本不跑
post-commit",并写进 commit message 和三处注释。**那次 revert 压根没产生 commit**,所以没有
钩子有机会运行。

台账第五轮就记过"复现失败要归因"。我记下了那条规则,然后在同一轮里对着一个坏探针违反了它。

### 5.4 引用必须支持结论,不只是"本身为真"

"cache_write 约为读的 5.6 倍"我引用了六处,每处都拿 tag4 的 token 计数当依据 —— 那组数只确定
了哪个 tag 承载 cache-write,**对成本一个字都没说**。比例本身站得住(17.8% of miss,1/0.178),
但我引的不是它。

**两句话各自都真、而推不出彼此,引用仍然是错的 —— 而且比不给引用更危险,因为它看起来可核。**

### 5.5 并发 agent 会吃掉未提交的改动

复核 agent 的 `git checkout HEAD -- src/x.js` 清理会把你未提交的编辑一起还原。本轮真发生了:
一个 commit 的 message 声称改了 `auth.js` 而 diff 里没有。

**动作**:让并发 agent 在 **worktree** 里跑(`isolation: 'worktree'`),或者改完立刻 commit;
commit 后核一次 `git show --stat HEAD -- <file>`。同理:**持有未提交改动时不要跑
`git reset --hard`** —— 我自己的测试清理也吃掉过一次。

### 5.6 N 项合取的谓词,spec 要逐项各有一条突变

`tiedWithFirst` 五项判据,spec 一开始只隔离了两项。逐个查下去四项都承重,其中 quota 那项
**没有任何 fixture 能让它说话**(种子账号没 `credits`,`quotaScore` 恒返回 100)。

**一项在所有 fixture 里恒等,不等于它不承重 —— 那只说明 fixture 不够。**

- 长命令必须真正后台跑;本会话前半段工具层反复返回空输出,全在多分钟阻塞命令之后
