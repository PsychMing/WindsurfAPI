## 1. 最要紧的一件事:v3.9.0 是坏的,应尽快发 v3.9.1

**已发布的 v3.9.0 里,它自己的头号功能对最常见的客户端形态完全不可用。**

**不发 `user` / `prompt_cache_key` 的标准 OpenAI SDK 客户端每轮链式必 404**。

已在 `30485c3` 修复。这是 v3.9.1 的主要理由。

### v3.9.2 之后又一轮(v3.9.3)

补跑复核期间自查发现:**v3.9.2 的 blocker 修复只覆盖了 3 条内部路由里的 1 条。**
`messages.js` / `gemini.js` 各自都有为同一场景写的守卫,都被同一个合成终止帧骗过
(实测 `stop_reason:end_turn` / `finishReason:STOP`,均无 error 帧)。已在 `161c88d` 修掉。

**根因比标记更深一层**:`finishPartialStreamAfterError` 除了合成 `finish_reason`,
**还会写 `[DONE]`**,而这两条路由都把裸 `[DONE]` 当权威终止信号 —— 所以有**两个**入口
被骗,只堵一个无效。我第一次尝试只堵了 finish 帧,验证"看起来没生效"因而一度误判回滚,
直到把两个入口一起折价才生效。(`responses.js` 对 `[DONE]` 是 `continue`,本就没这问题。)

**这是"修复只覆盖部分路由"的第 4 次,而且不完整修复就在上一个修复里。** 因此新守卫
加了一条**源码级元守卫**:任何内部 translator 不消费 `__synthetic_finish` 直接失败。

**给下一个接手的人的操作性结论**:改动"流终止/完成语义"时,必须逐条核对
(a) 四条协议路由,(b) 流式 vs 非流式,(c) **每个终止信号的所有入口**
(finish_reason 帧 / 裸 `[DONE]` / 错误帧)。只核对 (a) 已经不够了 —— 这一轮的两次
返工都是漏了 (c)。

### v3.9.4:检索端点自发布起不可用(把 bug 写成了契约)

补跑复核期间自查发现:v3.9.1 加的 `GET`/`DELETE /v1/responses/{id}`
**从发布起对所有客户端都必然 404**。无 body 的请求用
`callerKeyFromRequest(req, token, null)` 派生身份,而能链式的客户端 POST 时带
`:user:<hash>`、bodyless GET 派生 `:client:<ip+ua>`,键不同;不带身份信号的客户端
两边键相同却过不了 `hasPerUserScope`。`SINGLE_TENANT_CACHE=1` 也救不了。已在
`4a4653d` 修掉:身份信号改走 query(`?user=` / `?prompt_cache_key=` /
`?safety_identifier=`),与 POST body 同一套词汇、同一条提取路径。

**最该记的一条:它带着全绿的测试发布,是因为我把 bug 固化成了契约。** 那条路由层
测试断言"bodyless GET 必须 404",注释里还写着 "the documented contract"。测到的
现象是真的,对现象的解释是错的 —— 功能死了、测试却绿,而且后来读到它的人会以为
这是设计意图。

**规律**:写测试时必须区分"我在断言**期望**行为"和"我在记录**当前**行为"。
后者必须在注释里标明是观察而非契约,否则它会伪装成结论,并为 bug 背书。
(这与本文档 §5.4 的"假测试"是同类但不同种:那些是**测不到**,这条是**测错了方向**。)

## 5. 方法论(这一轮最值钱的产出)

### 5.1 被审过的地方是硬的,没审过的地方才有货

- 鉴权面 30+ 次绕过尝试、协议层 190+ 次 fuzz → **零缺陷**(都被审过多轮)
- 同期新写的 response store,一用真实 agent 循环压测 → **立刻出真 bug**

审计预算应优先投向**新代码**和**从未被真实客户端走过的路径**。老代码的价值在于把
不变式**守卫住**(见台账 🛡 标记),而不是反复重扫。

### 5.2 用真实客户端跑真实任务,比读代码有效

response store 的 tool_calls 重复缺陷靠单元测试发现不了 —— 它只在真实多轮工具循环
里出现,症状还是个与"账号已死"无法区分的不透明 503。

### 5.3 自己的修复必须被对抗验证

这一轮派 9 个 agent 证伪我自己的修复,结果:**每个原始缺陷都是真的(无幻觉),但
我的修法有一半不对,并且引入了 1 个 blocker + 4 个 major。**

具体我引入的:字节驱逐冲掉其他租户的会话、驱逐吃掉刚写入的条目、`approxBytes` 对
base64 图片完全盲视、CJK 低估 2 倍、instructions 去重保留已撤销的指令、空输入守卫
可被绕过且过度拒绝、legacy `role:'function'` 被误拒。

**"修好了"和"没修坏"是两个独立命题,后者必须单独验证。**

### 5.4 突变测试的三条硬教训

1. **一条从未失败过的测试等于没有测试。** 本轮发现自己写了三条假测试:一条恒真
   断言(检查的字符串在整个仓库都不存在)、两条镜像实现(在测试里复刻生产算术,
   生产退化不会失败)。修法:把逻辑抽成**导出的纯函数**,生产与测试共用同一份 ——
   不要在测试里复刻。
2. **突变覆盖不到的路径,它也证明不了那是死代码。** 我曾把一个自我驱逐守卫当死代码
   删掉,依据是突变验证"移除后行为不变"—— 但那次突变只走到无租户扫描路径,
   `oldestId(tenant)` 那条从未被覆盖,而它恰恰是守卫真正生效的地方。
3. **突变本身会写错。** 有两次我用了恒真条件(如 `>= 1`)做突变,那反而比原 bug
   更安全,于是误判"测试弱"。必须用**真实的原始错误形态**做突变。

### 5.5 注释里的夸大和代码里的 bug 一样有害

我曾在代码注释里写"可逐个打空账号池",而 `lastAccountExempt` 默认保证每 tier 留一个
存活 —— 实际是"降级到单账号"。下一个读者会照着错误的威胁模型做判断。**改代码时
一并检查它引用的注释是否还成立**(本轮修掉两处过期注释:一处声称流式总是发
`response.completed`,一处声称用了已被弃用的 Symbol 方案)。

### 5.6 反复出现的两个结构陷阱(已做成 CI 守卫)

- **`modelKey=null` 陷阱**(已 3 次):connect 选号恒传 `modelKey=null`,任何写在
  model 维度的状态对它结构性不可见。守卫:`test/connect-dimension-guard.test.js`
- **修复只覆盖部分协议路由**(已 2 次):四条 handler 各有翻译层。守卫:
  `test/handler-route-parity-guard.test.js`,含一条元守卫 —— 新增流式路由不登记即失败

### 5.7 会话操作纪律(踩过的坑)

- **严禁遍历删账号**。我曾在测试清理里写 `getAccountList().map(removeAccount)`,
  把用户的真账号一起删了,且**无法恢复**(项目刻意不记录 token,这是正确的安全设计)。
  清理只按自己创建的 id。
- **不要 `--amend` 已推送的 commit**(需要强推,项目规则要求先确认)。改成追加一个
  新 commit,历史只增不改。
- 全量 `npm test` 的计数会因 `--test-force-exit` 输出竞态波动(同一棵树见过
  2924/2952)。**权威口径是 `npm run test:release`**(逐文件进程隔离)。见到总数
  波动先重跑再怀疑代码。
- 测试文件里别写字面控制字符 —— 一个 NUL 曾让 git 把整个测试文件归类为 binary
  (diff 不可读)。用 `\0` 转义。
