## 协议层 (2026-07-27)

| 模块 | 行数 | 状态 | 依据 |
|---|---|---|---|
| `src/proto.js` | 178 | ✅🛡 | 18 类畸形输入 fuzz 全部可控抛出、无慢路径 |
| `src/connect.js` | 170 | ✅🛡 | 帧层 10 类畸形输入;gzip 炸弹(80MB→7ms 抛错,RSS 受控) |
| `src/proto-trace.js` | 907 | ✅ | 2000 层深度炸弹 1ms 内被深度上限截住,零栈溢出 |
| `src/windsurf.js` | 1540 | ✅ | 170 次畸形帧调用(见下),零栈溢出、零非受控抛出 |
| `src/cascade-native-bridge.js` | 1525 | ✅ | 同上;另核实 30+ 处 `parseFields` 消费者**无一自递归** |
| `src/grpc.js` | 457 | ✅ | trailer 解码已有测试;HTTP/2 会话池按 port 复用、error/close 即摘除 |

**探测方式**:对每个模块的每个导出函数喂 5 类恶意载荷(1500 层嵌套炸弹、8KB
随机字节、全 0、全 0xFF、空 buffer),共 170 次调用,断言无栈溢出、无非 `Error`
抛出、RSS 受控(67MB)。

**关键设计发现(值得保留的知识)**:

- `parseFields` 是**扁平**的 —— 嵌套消息以 `subarray` 交回调用方,由调用方决定是否
  下钻。这是深度炸弹打不穿协议层的根本原因:递归深度由调用方的业务逻辑决定,而
  那些消费者经核实无一自递归。**任何把 `parseFields` 改成自动递归的重构都会引入
  栈溢出面。**
- `decodeVarint` 走双路径:≤28 位用整数快路(覆盖全部字段 tag 和多数小整数),
  超出转 BigInt。这不是优化洁癖 —— `>>>` 会把 >2^31 的值静默截断成 uint32,
  request_id / 时间戳 / 计费计数器都会算错。
- 未知/废弃 wire type(3/4/6/7)**拒绝而非跳过**。跳过会让解析器失步,后续所有
  字段错位 —— 比直接失败危险得多。
- `connect.js` 的 gzip 上限加在**解压后**(`maxOutputLength`),不只是线长。通过
  16MB 线长检查的高压缩比帧仍可膨胀到 GB 级;没有这层,低内存主机上 OOM-killer
  会在 throw 被 catch 之前先杀进程(audit CONN-1)。

**守卫**:`test/proto-codec-hardening.test.js`(20 条)。突变验证 4 种退化:
移除 len-delim 越界检查(抓 2)、未知 wire type 改静默跳过(抓 1)、移除 varint
64 位溢出守卫(抓 1)、负数走 int32 截断(抓 2)。
`test/connect.test.js` 已覆盖帧层炸弹(8 条,先前既有)。

## 鉴权与暴露面 (2026-07-27)

| 面 | 状态 | 依据 |
|---|---|---|
| 运维端点鉴权 | ✅ | 无凭据 / 用 chat API key 冒充 dashboard 密码 → 全 401 |
| 路径归一化 | ✅🛡 | 前缀混淆、`../`、`%2e%2e`、`//`、大小写、`/v1/v1/` 重写链 → 全 401 |
| 静态文件穿越 | ✅🛡 | locale 白名单;`../../.env`、`%2e%2e%2f`、`....//` → 401/400 |
| SSRF | ✅ | `169.254.169.254` / `127.0.0.1:22` / 私网段 / `metadata.google.internal` → 全 `ERR_PROXY_PRIVATE_IP` |
| 暴力破解 | ✅ | 5–8 次后 429;**伪造 XFF 无法绕过桶**;锁定期内正确密码同样被挡 |
| 请求体 / 畸形 JSON | ✅ | 12MB → 413(`data` 事件即时中断);2000 层嵌套 → 400;截断 JSON → 400 |
| 密钥泄漏 | ✅ | 6 端点 + 日志文件对上游 token / dashboard 密码 / API key **零命中** |

共 30+ 次绕过尝试,全部被拦。

**关键设计发现**:

- **SSRF 防护是"先解析再判定"**:`metadata.google.internal` 的 `latencyMs=4` 说明
  真做了 DNS 解析,再按解析出的私网 IP 拒绝 —— 不是字符串黑名单。所以
  **DNS rebinding 也挡得住**。改成字符串匹配会静默退化。
- **`safeEqualString` 连长度泄漏都堵了**:先 sha256 再 `timingSafeEqual`,两边永远
  等长;`verifyPassword` 的明文路径在长度不等时还刻意烧等量周期。
- 路由层用 `===` 精确匹配 + `path` **从不 URL 解码**。这是路径穿越打不进来的原因:
  `%2e%2e` 保持字面,匹配不上任何精确路由。**任何"顺手"加归一化/解码的重构都会
  打开经典双解码绕过。**
- `/dashboard/api/` 前缀**带尾斜杠**。少了它,`/dashboard/apiaccounts` 会被
  `slice` 成伪 subpath。

**守卫**:`test/router-path-security.test.js`(11 条,突变验证 4 种绕过:加 URL
解码抓 2、前缀去尾斜杠抓 1、`===` 放宽成 `startsWith` 抓 1、locale 白名单放宽抓 1)。
另有既有的 10 个安全测试文件(`dashboard-auth-fail-closed` / `-hardening` /
`brute-force` / `lockout-map-bound` / `server-auth` / `auth-safe-equal-hash` /
`dashboard-proxy-validate` / `caller-key-xff-spoof` / `xff-client-ip-consistency` /
`local-windsurf-security`)。

**审计缺口的教训**:上述既有 10 个套件全部直接 `import handleDashboardApi` ——
它们证明了**鉴权逻辑**正确,却从未走过 `server.js` 里决定"哪个 URL 进哪个 handler"
的**路由层**。这类"测了逻辑、没测装配"的缺口值得主动找。

### 2026-07-28 补扫:流终止与 finish_reason 语义

接手会话把交接文档 §3 的 1–7 全部修完。这一批的共同主题值得单独记一条:

| 面 | 状态 | 依据 |
|---|---|---|
| 连接层流终止 | ⚠️🛡 | 缺 end-of-stream 帧被当作正常抽干 → 截断回复以"完整一轮"到达四条协议路由。现抛 `STREAM_TRUNCATED`;守卫 `test/responses-stream-truncation.test.js`(12 条,突变验证 3 种) |
| `finish_reason` 词汇映射 | ⚠️🛡 | 三处独立缺陷同源:未校准枚举猜测(connect 3/5)、子串匹配(special-agent `'content'`)、缺失即良性(responses translator)。守卫见各 commit |
| 响应检索端点作用域 | ✅🛡 | `GET`/`DELETE /v1/responses/{id}` 与续接同一套作用域;外来 id 一律 404 不泄漏存在性;路由层另有真实 HTTP 测试 |

**新的规律(值得记住)**:这一批里有三个缺陷是同一个错误模式的不同外衣 ——
**把"不知道"当成"没事"**。缺失的终止帧当成正常结束、未校准的枚举值当成已知语义、
缺失的 finish_reason 当成良性完成。三处都在"信息不足"时选了乐观解释,而代价都是
把坏结果报成好结果。遇到任何"默认值/兜底"分支时值得专门问一句:这个默认是在
断言事实,还是在承认无知?

**方法论补充(与 §5.4 突变教训同类)**:修复过程中发现三条既有测试写死了错误
前提 —— `connect-usage-finish-calibration` 断言 `3 → length`(照名字顺序的猜测)、
`responses.test.js` 一条 mock 不发终止 chunk、`request-id-body` 写死站点计数 4。
前两条是**把猜测固化成契约**:一旦写进断言,后来的人会把它当既有结论而不是待验证
假设。写这类测试时应当在注释里标明"这是猜测,证据是 X",否则它会伪装成事实。

**关键教训**:这批缺陷有一半是**我修复上一批时新引入的**。详见
[HANDOFF-2026-07-27.md](HANDOFF-2026-07-27.md) §5.3–5.4 —— "修好了"和"没修坏"是两个
独立命题;以及三条突变测试的硬教训(假测试、突变覆盖不到的路径、突变本身写错)。

## 方法论笔记

这轮最有价值的规律:**被审过的地方是硬的,没审过的地方才有货。**

- 鉴权面 30+ 次探测、协议层 190+ 次 fuzz → **零缺陷**(都被审过多轮)
- 同期新写的 response store,一用真实 agent 循环压测 → **立刻出真 bug**

推论:审计预算应优先投向**新代码**和**从未被真实客户端走过的路径**,而不是继续
扫老代码。老代码的价值在于把它的不变式**守卫住**(上表 🛡),而不是反复重扫。

第二条:**用真实客户端跑真实任务**比读代码有效。response store 的
tool_calls 重复缺陷靠单元测试发现不了 —— 它只在一个真实 agent 多轮工具循环里
出现,且症状是一个与"账号已死"无法区分的不透明 503。

### 2026-07-30 补扫:测试自身的质量

复核唯一跑成功的那一面审的是**测试**而非代码,5 条全部经独立突变验证成立。这一节记的
不是某个缺陷,而是三类**测试反模式** —— 它们让全绿的套件失去意义:

| 反模式 | 识别方法 | 实例 |
|---|---|---|
| **源码 grep 冒充行为守卫** | 断言里只有 `assert.match(src, /.../)` 或 `src.includes(...)`,而被守的是**行为** | 破坏 header 名派生 → 6 个信号里 4 个 404,35 个测试全绿 |
| **条件断言** | `if (X) { assert A } else { assert B }` —— 只能证明恰好走到的那一支 | DELETE 端点整个失效,套件 11/11 全绿 |
| **恒真断言** | 断言的字面量在 src 里根本不存在 | `doesNotMatch(html, /pageSize=1000/)`,而实际写法是 `pageSize: '1000'` |

**源码 grep 的正当用途是守结构性不变量**(如"新增内部路由必须消费 `__synthetic_finish`"、
"每个上游错误码必须有明确的归属分支")—— 那类命题本来就无法用行为测试表达,因为要守的
代码还没被写出来。但它不能替代行为验证。

**判别标准**:问"如果这个功能完全坏掉,这条断言会失败吗?"如果答案依赖"字符串还在
文件里",它就不是守卫。

### 2026-07-30 方法论:追问同类 + 报告者必须被独立验证

**一、修掉一个误落进兜底的东西之后,必须枚举还有什么在下面。**
v3.9.2 修了 `STREAM_TRUNCATED` 落进 `finalizeConnectAccount` 的裸 `else reportError`,
但只修了那一个码。这轮枚举全部 12 个上游错误码,又找出三个(`TIMEOUT` /
`DEADLINE_EXCEEDED` / `NO_TOKEN`),各 3 次调用即把健康账号打成 `status='error'`。

1. **"两个行产出器都过滤"** —— live 目录在新进程里是空的,producer 2 压根不产行,断言无论

## 2026-08-04 第七轮:sticky 两条积压 —— 一条不该修,一条修错了

本轮结论:**积压里剩的两条 sticky 项,一条正确答案是"不动",另一条我按显然的修法做完、
实测是净负面、已 revert。** 两条都从"待办"变成了"有依据的结论"。

### `clearCallerBindings` 无生产调用点 → 结论是"不接线"

台账此前记的是"事实成立,但该由哪个事件调用是设计决定"。查完是:**没有正确的事件**,
而且找它本身是错的问法。

| 候选触发点 | 结论 |
|---|---|
| 客户端断连 | **主动错误**。钩子确实存在(`server.js` 的 `res.on('close')` → abort),所以这是活着的诱惑。但 agent 客户端持续半途取消,而代码库其余部分刻意把取消当"什么都没发生":connect finalizer 对 abort 免除全部惩罚,`poolCheckin` 还把签出的 cascade 条目**放回池里**。在那里清绑定会亲手制造本模块存在意义所要防止的上下文丢失 —— 放回的条目仍带账号 X 的 apiKey,下一轮 checkout 要 Y,在 `conversation-pool.js` 的 apiKey 比较上 MISS,整段历史重放 |
| session reset | **不存在这个事件**。唯一 caller 维度的 DELETE 是 `DELETE /v1/responses/{id}`,删一条记录,无"会话结束"语义 |
| 账号离池 | 是真的清理,但它是**账号维度**的,需要另一个导出;而且**不值得加**(下面) |

**账号维度的清理也不值得加。** 绑定所指账号消失后它再也不会被刷新(`auth.js` 在解析它的
同一次调用里就清掉),于是单调老化到 LRU 前端、**最先**被驱逐。实测 `STICKY_SESSION_MAX=10`:
容量满时 4 死 + 6 活,再插 4 条 → 4 条死的全被驱逐、6 条活的全存活,与"提前回收"的存活集
**完全相同**。死绑定是免费的驱逐缓冲;提前回收反而会去驱逐活的。另外 `status='error'`
无论如何都是错的触发点 —— `maybeRecoverErrorAccount` 会把它半开回 `active`。

依据已写进 `sticky-session.js` 的注释(含实测数字),这条从积压里划掉。

### RPM 满即清绑定 → 显然的修法是净负面,已 revert

我先按显然的修法实现了:瞬时不可用(RPM / 冷却 / 维护)时保留绑定,并让返回对象带
`_stickyRotated`、四个写入点据此跳过替补轮的重钉(不加第二半,`setStickyBinding` 会无条件
覆盖,第一半等于没做)。12 条断言、9 次突变全 CAUGHT、门禁 3323/0。

**然后测了代价,方向是反的。** 6 轮受阻期间触达的不同账号数(每个不同账号 = 一次完整前缀
写,约为读的 5.6 倍 —— 依据是 `devin-connect.js` 的 "hit cost measured at 17.8% of
miss"(1/0.178),**不是**同处引用的 tag4 token 计数,那组数只确定哪个 tag 承载
cache-write):

| 做法 | pool=4 | pool=8 |
|---|---|---|
| 保留绑定(我的修复) | **4** | **3** |
| 清绑定(现状) | 2 | 2 |
| queue-on-pin(短等) | 1 | 1 |

机制是结构性的,不是偶然:清绑定**收敛** —— 替补成为新绑定,后续每轮读它的缓存;保留绑定
**散射** —— 每轮受阻请求重新进常规选择,而候选排序末位是 `lastUsed` **升序**,刚服务过的
替补被排到最后,下一轮必然换一个冷账号。实测 pool=4 序列 d→a→b→d→a→b。

只有抖动**短于相邻两轮间隔**时保留才划算。RPM 窗口 60 秒而 agentic 循环相邻轮隔几秒,所以
受阻 caller 通常连续多轮受阻 —— 正是保留会输的 regime。**而那恰好就是我自己在修复注释里
写的"自我强化"场景。**

已 revert,并留下 `sticky-transient-blip-tradeoff.test.js` 钉住现状 + 记下三方数字。承重
断言是"后续受阻轮复用同一个替补":把 revert 掉的修复打回去,5 条里 3 条失败。

### queue-on-pin 是正确答案,但它是产品取舍

对抗调查推翻了台账"彻底修需 queue-on-pin(言下之意不可行)"的判断 —— **它可行**:

- `getApiKey` 是同步的,但 `src/` 里只有 4 个调用点,改异步只需 1 个 `async` + 2 个
  `await`。真正的代价不是接线,是**原子性**:选择是池状态的纯函数,读与写之间插入任何
  `await` 都会重新引入 #37 要防的超订(实测把可见突变移除后,8 次并发取号对 5 个 callerKey
  全部塌成 1 个账号)。另有 19 个测试文件 55 处同步消费
- 所以钩子应该加在**异步调用方**(`waitForAccount` 头部,在第一次 `getApiKey` 之前 ——
  一旦它返回,绑定已经被清了)。**同样的模式在 cascade reuse 上已经上线两处**:
  `acquireAccountByKey` 返回 null 时 `for (w<10) { await sleep(500) }` 再降级
- 等多久不用猜:`getAccountAvailability` 已经按原因给出 `retryAfterMs` —— `rpm_full`
  1500ms、`rate_limited` 45s、`quota_exhausted` 10.8M ms。所以"等还是换"可以逐原因精确决定

**未做,因为它把 caller 的吞吐钉在单账号 RPM 上(pro 60/min、未探明 20/min),是延迟换缓存
成本。** 这是产品取舍,不是工程判断,列进"需作者拍板"。

### 判别动作:先问"这个修法在目标 regime 里的代价是多少",再写它

本轮最贵的一课。我的修复通过了每一道自设关卡 —— 12 条断言、9 次突变双向覆盖、门禁全绿 ——

## 2026-08-04 第八轮:queue-on-pin 落地 —— "产品取舍"是我升错了级

第七轮把 queue-on-pin 记成"产品取舍,需作者拍板"。**那是升错了级**:做成默认关的开关,
取舍就交给运维而不是代码,现有部署字节级不变。仓库对同类取舍本来就是这么处理的
(`STICKY_SESSION_ENABLED` / `stickyNoFallback` / `SINGLE_TENANT_CACHE` 全是 opt-in)。
作者一句"改成功能不就行了"点破的就是这一条。

**动作**:把一件事标成"需要拍板"之前,先问"它能不能做成默认关的开关"。能,就不是取舍,

### 方向验证(第七轮那条教训的第一次应用)

第七轮的教训是"突变验证不检查方向"。这一轮先测方向再定稿。同一场景,旋钮关 vs 开,
含两轮 warmup 让被绑账号真正持有前缀:

| | 序列 | 触达账号数 = 完整前缀写次数 |
|---|---|---|
| 关(现状) | `A,A,sub,sub,sub,sub,sub,sub` | **2** |
| 开 | `A,A,A,A,A,A,A,A` | **1** |

pool=4 与 pool=8 结果相同。对照第七轮被 revert 的"保留绑定"是 4 和 3 —— 同一个场景、
同一把尺子,方向相反。

**代价也测了**:每个受阻轮 **约 1 秒**。下界不是我们能选的 ——
`getAccountAvailability` 对 `retryAfterMs` 有 `Math.max(1000, ...)` 地板,所以一个
实际 400ms 就恢复的窗口也会报 1000ms。想突破得自己从 `_rpmHistory` 重算窗口,那是
把 auth.js 的逻辑复制一份,正是"只覆盖部分路径"的成因,不做。

一个被自己规则否掉的改动:我按 `retryAfterMs` 给首次 sleep 定长(而不是固定 1 秒
tick),测下来**墙钟没有变化**,只是少轮询几次。按"改行为前先测两个数字"的规矩,
没测出收益的优化不上车,已丢弃。

### 三个实现要点

1. **挂钩点是 `waitForAccount` 头部** —— 唯一的异步调用方,连接路径经
   `acquireConnectAccount`、两条 cascade 路径直接走它。必须在它第一次调 `getApiKey`
   **之前**,因为那次调用就是清绑定的地方
2. **`getApiKey(..., { pinOnly: true })` 复用真实的可用性合取判断**,而不是在等待循环
   旁边重写。它是绝对的:pinOnly 永不返回非绑定账号,连"压根没有绑定"时也不返回 ——
   否则循环会把替补当成自己的绑定并重钉上去,把等待悄悄变成它本要避免的换号
3. **只在账号自己声明的恢复时间放得进预算时才等**。reason 码本身不够用:`rpm_full`
   对窗口即将滚过的 caller 是 ~1.5s,对刚把配额一次性打满的是 ~59s

### 同一个突变形态本轮出现四次:守卫守在了错误的一侧

13 次突变里有 3 次漏网,全是同一形态 —— 断言测的是**被调用的函数**,不是**调用点**:

| 突变 | 漏网时的状态 | 补法 |
|---|---|---|
| 轮询改用 mutating 的 `getStickyBinding` | 三条 peek 测试全绿 | 驱动真实等待循环,断言一个排队轮恰好 +1 hit |
| 可用性探测丢掉 selector 维度 | 25/26 全绿 | 端到端只打 selector 维度冷却,断言仍等待 |
| `WAITABLE` 白名单整条删除 | 26/26 全绿 | **不补断言** —— 见下 |

前两条补成了端到端断言。第三条查下去发现**它今天真的守不住**:每个不可等的 reason 都把
`retryAfterMs` 写死 60000,而旋钮 max 是 30000,预算那道闸已经全挡了。所以白名单是
belt-and-braces,不是承重件。

本轮实测撞到全部三种,每种的正确反应不同 —— 读成同一回事,要么留着真洞,要么把计数凑饱满。

字符从来没承重过。处置:**补能通过前一道门的 fixture**(加了三条带反引号的:重定向、分号、

**外加一条钉住前提的测试**(扫源码断言没有非 global 规则带捕获组)。一个前提未被断言的漏网,
与一个没解释的洞**读起来一模一样**。

**判别动作**:看到 SURVIVED,按这个顺序问:①有没有更早的门拦掉了 fixture?②有没有哪个合取
条件没被同时满足?③这行今天有没有任何合法输入能驱动?**①②的答案是"补测试",③的答案是
"不要补"。** 前两种记成 `expectCaught: false` 就是留着真洞;第三种去补 fixture 则是在给
到不了的代码造入口。

### 二、未被断言的日志行与不存在的日志行无法区分

两个修复的**交付物本身就是可观测性**(一条 `log.warn`),而两处都没有任何测试驱动那行日志。
形态:把「拒绝时记日志」的判据**反转**(`!stored && wantsPersistence` → `!stored &&
!wantsPersistence`)的突变 SURVIVED —— 因为没有任何东西在观察日志,反转与不反转对测试完全
等价。

补法:`log.warn` 是可替换的,存原值 → 换成收集器 → `finally` 里还原。补了三条之后那条突变
CAUGHT fail=2;同一个洞在另一个修复上存在,同样补掉(删掉日志行的突变现在 CAUGHT fail=1)。

**这条对整个仓库成立,不只那两处。** 凡是「这个修复的价值在于让下次踩到时可见」,就必须有一条
测试捕获那行输出,否则下一个人删掉它、改窄它、或把判据写反,门禁都是绿的。

**判别动作**:一个修复如果没有改变任何返回值、只增加了日志,问「删掉这行日志,哪条测试会红?」
答不出来就等于没做。

### 三、`--test-force-exit` 在并发下静默截断计数,而 exit 仍是 0

同一棵树(shasum 逐字节相同)连跑门禁三次:**3685 → 3687 → 3687**。第一次少两条,而
`fail=0`、`EXIT=0`。逐文件核对:某个文件的 `ℹ suites` 行在中途被切断,整个 suite 没登记。

不是 harness 缺陷:`run-test-shard.mjs` 的 `ok: !timedOut && code === 0` 会把真超时变成
exit 1。机制是 `--test-force-exit` 在 stdout flush 完成前切断子进程,而子进程仍退 0。多个
worktree 并发跑门禁时(评审多个 PR 就会这样)最容易出现。

**判别动作**:`pass=N fail=0` 里的 N 会静默变小。**引用门禁数字时,`EXIT=0` 加上跨次稳定
才是证据,单次读数不是。** 算术不闭合(基线 + 新增 ≠ 现值)时,先跑第二遍再怀疑代码。

### 四、探针错三次,其中一次生产了一条假缺陷

同一轮里写坏三个探针:env 变量名写错(`WINDSURFAPI_` 而非 `DEVIN_CONNECT_`)、方法名写错
(`push` 而非 `feed`)、以及**把返回字符串的 `flush()` 当对象读 `.text`**。第三个报出
「未闭合 span 不按 text 放行」—— 一条**不存在的缺陷**,而且它与被审 spec 的声明矛盾。

识破靠的正是那个矛盾:一个 EXIT=0 的 spec 声明「flush 释放未闭合 span 为文本」,而我的探针说
它不释放,**两个信号只能有一个是真的**。台账第五轮记过同款(拿已知非零输入喂同一探针),这次
起作用的是另一个更便宜的动作。

**判别动作**:探针结论与被审对象自己的声明/测试矛盾时,**先怀疑探针**。尤其当结论「恰好支持
你想写的那句话」时 —— 那是最需要停下来的信号。

### 五、跨会话引用的数字会腐坏,而它读起来和刚测的一样

本轮我连续三次向用户报告「致谢页 / 多语言」的问题清单,四个数字里**三个是错的**:

| 我说的 | 实际(本轮 `shasum` / `node -p` 实测) |

## 2026-08-10 第十六轮:审计工具与被审对象共享同一个盲点

第十五轮的教训是"跨会话的数字要重测"。这一轮把它推进一步:**重测用的工具,可能和产生错误的
工具是同一个** —— 那样重测只会确认错误。三个发现全是这一类,加上两个合并 PR 时抓到的。

### 一、一个计数和它的守卫出自同一条正则,于是互相印证而不是印证代码

交接文档记着"86 个环境开关,86 个全部有文档",并且把用来数它的那条 grep 标成"对的方法"。
**两半都错:真实 156 个,47 个在四份面向读者的文档里都搜不到** —— 其中包括上一轮新增的
**全部 5 个 wire 坐标开关**(`#13` prompt 缓存、`#12`/`#11` tool_choice、三个 signature tag、
两条路径的 user_jwt)。恰恰是最需要写清"tag 号来自 `.proto` 声明顺序而非抓包,所以默认关是
刻意的"那一批,而这段说明当时只存在于源码注释里。

成因是那条 grep 只认 `env.FOO`,而漏掉的 70 个恰好写成 `positiveIntEnv('FOO', 默认)` 和
`runtime-config.js` 里 `{env:'FOO', kind:'bool', def:true}` 的表驱动声明。**数字和覆盖率
出自同一个正则,所以"数一遍确认"这个动作本身没有独立性。**

同一个盲点在默认开台账里是**第四次**出现(`a98a572` `3af3f63` `c374ec7` 是前三次):它四个
发现模式都要求字面 `env.NAME` 紧邻 `'0'`/`'1'`,于是六个默认开开关带着绿灯上线 ——
`WINDSURFAPI_BREAKER`(关掉=坏账号永不摘除)和 `_SPEND_ON_DEMAND`(真实花钱)在内。

修:`93b38f9`(47 个补文档 + 正确数法写进 `docs/ENV-SWITCHES.md` 头部)、`c445c9d`(台账补
表驱动模式)、`d367a50`(新增 src→文档 方向的守卫)。原守卫只做"散文提到 → 必须在
`.env.example`",反方向注释里承认是盲区,理由是"正则会有几百个误报" —— 限定三前缀 + 只匹配
本仓库实际用的读取形式 + 先剥注释后,**实测零误报**。

### 二、我犯了同一个错误的**反面**,并据此写了一整个重复的测试文件

搜**环境变量名**得出"degraded serve 没有关闭路径测试",是错的:表驱动开关的关闭路径测试走的是

结论把测试写完了,才发现 `devin-connect-breaker.test.js` 早就测了,已删除。

一个实体两个合法名字,搜一个然后从沉默里下结论 —— 和上面那条是同一个错误指向相反方向。
`hasOffPathTest` 现在两个名字都认,别名映射**从表里读**而不是手写,并断言解析出 ≥20 条:
映射变空不会让任何测试变红,只会让真实测试重新隐形,是往"安全"方向的静默失效。

顺带纠正一处源码注释:`src/auth.js` 写着 degraded serve "Default OFF … until an operator

### 三、合并 PR 暴露的两个新变体

**(a) PR 的两处改动互相抵消。** `#252` 加了 `conflictsWithKimiPreamble()` 在 Kimi 前导下跳过
XML 强化段,又把 `toolReinforcement` 默认值换成一句泛泛的话。问题是**第一件的检测条件就是
"强化段里含 `<tool_call>`",而第二件把这个 marker 删了** —— 实测合并后隔离函数在默认配置下
永远返回 false,代码永远不执行。PR 真正生效的机制是"把冲突文本从全局默认值里删干净",不是它
声称的按方言跳过;而 `toolReinforcement` 是**无条件**拼给所有带工具的 Cascade 请求的,代价是
所有非 Kimi 方言一起失去格式示范。已还原(`0523910`),隔离函数开始真正触发,`#252` 涉及的
137 个测试仍全过。

原有测试用 `setSystemPrompts` **注入**含 marker 的文本,证明抑制**能**工作但没证明它**会被
触发** —— 默认值不带 marker 时抑制静默变 no-op,那条测试照样绿。**一个开不了火的守卫,和一个
通过了的守卫,看起来一模一样。**

**(b) 守卫的第五种读取形式,`#249` 一进来就漏掉了。** 它写
`export const LEAK_TRACE_ENV = 'WINDSURFAPI_LEAK_TRACE'` 然后 `env[LEAK_TRACE_ENV]` ——
读取点是**常量名**,四种模式全看不见。它自己文档写全了,于是守卫绿着、统计却少算一个,
正是这道守卫要防的失效从它不看的那扇门进来(`1fbefd0`)。开关数 156 → 157。

### 四、一条测试里两个随机失败,合起来约 7%

`test/getuserjwt.test.js` 的 `buildMetadata` 断言。`3c1a173` 引入时就带着,一直概率性通过,
合并后的全量恰好掀到 —— **第一反应是"合并破坏了什么",错的**。`buildMetadata` 有个随机字段,
两次同参调用**内容和长度都会变**(实测长度在 73/74/75 之间)。

- 扫裸 `0xaa` 字节判定"字段 21 存在":2000 次实测 **4.3%** 假失败。tag 字节只有落在字段
  边界上才是 tag,任意字段 *值* 的任意一字节都可能是 `0xaa`。
- `without.length === plain.length` 判定"显式 null 不加字段":5000 次实测 **3.3%**。

台账第十一轮记过"断言 wire 不变要用字段不存在,不能用字节相等",**但比长度、扫单字节是同一个
坑的变体,规则那样写没拦住**。都改成断言解析出的字段结构(`f91d54b` `62dec04`),修后连跑
60 次 0 失败。

突变验证走了两轮才对:先试 `if (userJwt)` → `if (userJwt !== undefined)`,**SURVIVED** ——
但那是第十五轮 (c) 类的**无效突变**,传 null 时 `writeStringField` 本来就产不出字段,突变体
与原文行为等价。换成真会写出字段 21 的突变才变红。

### 判别动作

- **在信任一次扫描之前,先证明它能看见。** 往真实文件里追加一个已知坏样本,每种本仓库实际
  用的形态各一个,要求守卫**逐个变红**;再检查一个近似但合法的样本(前缀碰撞、纯注释提及)
  **保持绿**。这一轮五个探针几分钟就跑完,抓出两个真缺陷。
- **一个计数和执行它的守卫不要共用一条正则。** 共用时绿灯只说明它们彼此一致。
- **从派生查找表得出的结论,要给表本身加计数断言。** 表变空是往"安全"方向静默失效。
- **扫描说某样东西不存在时,先问它可能在另一个名字下面。** 同一个开关有 env 名和字段名两种
  合法写法。
- **加了条件行为,要检查出厂默认值仍然满足那个条件**,并用**真实默认值**跑端到端断言,不要用
  注入的 fixture。
- **间歇性失败在合并后出现,先用几千次直接调用量化**,再怀疑合并。

### 判别动作

- **并发原语:身份不能是路径。** 只要"谁持有"靠**第二次写**(`owner.json`)或固定路径上的重读决定,
  回收就不可能安全:总有一个窗口让两个参与者对同一个名字得出不同结论。身份写进**不可变实例名**

- **每一个"与上一个 release 比较"的门禁,都要断言基线 SHA ≠ HEAD**,并对**选择器本身**写测试:
