## 2. v3.9.14 发了什么

### `#240`:一次 thinking-only 救援会吃掉空回复重试的预算

`streamChatWithEmptyRetry` 里两条投机重发的臂各有上限,但共用循环计数器:救援臂一直有独立
的 `rescueAttempt`/`rescueMax`,而空回复臂的判据读 `for (…; ; attempt++)` 的 `attempt`,两条
臂都靠 `continue` 进下一轮 —— 于是每次救援顺带花掉空回复的预算。**单向**。

默认值下:2 次救援后遇空回复 → 客户端收到 `""`;同一个空回复前面无救援 → 治好。

**判定它是非预期耦合而不是刻意策略,依据在代码本身:救援臂自带一对计数器。** 共享一个池
的设计不需要第二个。遇到"这个耦合是不是故意的"先找**冗余** —— 如果按"刻意"的解释某个既有
结构是多余的,那个解释大概是错的。

**总上限刻意不变**(`1 + max + rescueMax`)。它拆分前**就已经够得到**,只在"先空回复"那个
顺序上;所以饿死不是"上限太低",是"上限的花法依赖顺序"。

**一个把饿死"修"成抬高上限的改动,在只测饿死的测试里长得一模一样** —— 所以两个方向各有
断言。

报告者 warelik 附 66 天生产数据(158 次 empty-retry、6 次救援、零次可归因的耗尽)。

### 工具:`FORCE_COLOR` 让 `mutate-verify` 恒报"你的套件不绿"

node 给汇总行套 SGR 码,而计数正则锚在行首行尾 → 恒得 `pass=0` → guard 2 拒绝启动。**失败
在安全侧**(0 计数造不出假 SURVIVED),但报错把责任推给套件。

带 `FORCE_COLOR=3` 时 `test/mutate-verify-harness.test.js` 自己 **6/10 红** —— 门禁此前绿只
因环境恰好没设这个变量。修好后带该变量跑全量门禁确认封口。

**如果你的 shell 或 CI 导出 `FORCE_COLOR`,v3.9.14 之前的 `npm run mutate` 在你机器上从来
没真的跑过。**

## 5. 本轮学到的

台账第十一轮有完整版。两条最会直接害到下一个人的:

### 5.1 突变的 CAUGHT 计数是跨文件求和的,别用它推断"我这条断言咬住了"

按第六轮的标准逐条查 12 条断言有没有空转,查出四条,其中一条**不是冗余而是坏的**:

"主开关覆盖两条臂"那条,**把主开关从空回复臂删掉它照样通过**。第一轮我传的是
thinking-only,而救援预算此时已是 0,那一轮既不可救援也不算空,请求在第 1 次调用就结束 ——
空回复臂的判据压根没被走到。它对自己命名的那件事零断言。

而工具当时报的是 `CAUGHT 1` —— 那 1 条失败来自**另一个文件**。工具每条突变只打印前 4 个
失败名、且混着 suite 名,所以看不出来。**要按叶子测试名逐条收。**

### 5.2 探针给出"零/空"时,先拿已知非零的输入喂同一个探针

本轮我自己写坏四个探针,全部表现为空输出或零结果:POSIX awk 不支持 `\s`(差点据此断言"没有
重新赋值")、拿一个在旧基线上不存在的测试文件当探针(node 什么都没跑)、`parseFields` 是返回
数组不收回调(差点据此写"解码侧静默丢掉字段 0",实际它原样产出)、门禁计数用 `tail -40`
截掉了汇总。

第五轮就记过"没看到信号先问探针坏没坏"。**四次里有三次我的第一反应仍是"被测对象没有那个
性质"。** 唯一让我快速识破的是第三次 —— 因为那个结论听起来太好,正好支持我想写的那句话。

**动作**:比复查逻辑更快的是喂一个已知非零的输入进去。它同时验证探针和被测对象。
