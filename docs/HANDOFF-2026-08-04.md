## 1. 本轮做完了什么

### v3.9.10 — 两条真实账号跑出来的缺陷

**订阅取消对账号池不可见。** 一个订阅已取消的账号会静默吞掉所有 chat 请求,而 Dashboard
显示 `active` / `错误 0` / 宣传 163 个模型。实测三个 RPC 三种结果:

```
目录 RPC        200 → 167 个 selector   (不检查 entitlement)
GetUserStatus   403 → "Your subscription has been canceled"
GetChatMessage  CAPACITY ×2 → UPSTREAM_INTERNAL "an internal error occurred"
```

chat 的失败被归类 `UPSTREAM_INTERNAL` 且**刻意不记账号**(一次上游抖动不该打下整池,那条
规则是对的),所以唯一知道原因的 RPC 把它写进 `credits.lastError` 后没人读。

处置机制本来就有(`looksLikeBanSignal` 匹配、`reportBanSignal` 要求 30 分钟内两次),缺的
只是一条线。`refreshAllCredits` 15 分钟一轮,真取消会在相邻两轮命中两次;瞬时错误不匹配
正则(`an internal error occurred` / `CAPACITY` / `DEADLINE_EXCEEDED` 全 false)。

**恢复路径**:`PATCH /accounts/:id {resetErrors:true}`(Dashboard 的"重置"按钮)→ `active`。

**降级后谎报模型名,三条协议路由。** `STRICT_MODEL=0` 把未映射模型降级到免费 selector,
但响应把请求的**付费名**报回去。`messages.js` / `gemini.js` 对 `displayModel` 的引用数原本
都是 **0**。

流式的修法:translator 在上游结果之前构造,所以从**第一个 chunk** 学真名(OpenAI 每个
chunk 都带 `model`,`message_start` 是懒发的)。

**一个反直觉的点**:上一份交接 §3.6 写的是"报实际跑的 selector"。**照做会把一个谎言换成
另一个** —— `selector` 在 AssignModel router 跳转之前就被捕获,而 router 名解析为
`mapped:false`,所以实际跑了 `claude-opus-4-8-medium` 的 `adaptive` 请求会被报成免费的
`swe-1-6-slow`。用的是跳转后的 `connectParams.model`。

### v3.9.11 — 守卫与 sticky 积压

**`stickyNoFallback` 永久楔死 caller。** 返回 `null` 却把绑定留在原地,后续每次请求重新
解析同一个死绑定再次拒绝。实测:disable 绑定账号后连续四次全 `null` 且绑定仍在。

修法区分**结构性消失**(清绑定)与**瞬时不可用**(拒绝并保留)。两半都钉了测试 —— 只修
第一半会把 flag 变成 no-op。

**路由错误分类的源码守卫可被绕过。** 判据是"绑定名出现 >1 次",任何第二次提及都能满足。
实测:接线改回读扁平 `err.type` + 留一个被 `console.log` 读到的死绑定 → 守卫 10/10 全绿。
新增行为断言,同一突变下 6 条失败。

## 3. 对上一份交接的修正(接手时最要紧)

### 3.1 "两个 flag 全开才楔住" —— 错,一个就够

上一份 §3.10-3 记的是"需两个实验 flag 全开"。实测:

```
无 flag                    → 自愈
仅 stickyNoFallback        → 楔住     ← 一个就够
仅 stickyBindByUserOnly    → 自愈
两个都开                    → 楔住
```

`stickyBindByUserOnly` 与楔子**无关**。暴露面比记录的大 —— 只开一个文档化的 flag 就会
永久硬失败。已修 + 钉测试。

### 3.2 首轮 thundering-herd 不是缺陷,是设计张力

上一份 §3.10-1 把它列为待修。现象复现了(8 次同 caller 取号 → 8 个不同账号、0 sticky
hit),但**散射是明确写在代码里的意图**:

```
// Pick the account with the fewest in-flight requests first (so a burst
// of concurrent calls spreads across accounts ... — see issue #37).
```

把首轮绑到一个账号会违反 #37,并把并发串行到单账号 RPM 上限。而代理**分不出**"一个会话
的 8 个并行工具调用"(想要一个账号)和"8 个独立会话"(想要 8 个账号)。

两侧此前都没记过这个张力。交付改成:两侧互相引用地写下 + 测试钉住当前选择,让未来改动
任何一侧都是自觉的。**不要把它当缺陷去"修"** —— 先读 `sticky-session.js` 的 CONCURRENCY
注释。

### 3.3 `STRICT_MODEL=0` 那条测试并未把缺陷固化成契约

上一份说 `devin-connect-strict-model.test.js` "把这个行为断言成期望行为"。核实后不成立:
那条测试只断言"opt-out 不得 400"(这正是 opt-out 的正当用途),对 `.model` 的断言数为
**0**。所以谎言是没有断言覆盖的,修它不需要跟测试打架。已修。

### 3.4 门禁数字三处错

`3245 / 3195 / 3254` 都是中间分支读数被当成发布基线。权威表见 §0。两份 release notes、
两个已发布的 GitHub Release body、三条 issue 回复都已更正。

## 6. 本轮新增的方法论

上一份 §4 仍然有效。这里只补它没有的。

### 6.1 长任务必须后台跑 + 短轮询

本会话前半段工具层反复返回**空输出**,全部出现在多分钟阻塞命令之后(`npm run test:release`
单次 15 分钟以上)。改成 `nohup ... &` + 轮询标记文件后再没出现过。

十项机制逐个测过(stdout / stderr / exit code / cd / git / node / python / heredoc)都正常
—— 问题是**用法**,不是工具坏了。

### 6.2 "先提交,再突变" —— 本轮违反了三次

突变循环里的 `git checkout -- <file>` 会把同一文件里**尚未提交的真修复**一起还原。之后的
突变测的是"修复缺失"而不是"突变生效",而那个失败**看起来像突变被抓到**。

三次都是我自己踩的。纪律:修复先 commit,再跑突变。

### 6.3 harness 静默失效的三种新形态

除了上一份记的 zsh 词分裂,本轮又踩到三种:

1. **`import(...?query)` 创建独立模块实例** —— 我拿 sticky 模块的新实例写绑定,而 auth.js
   用它自己的静态导入读 → 统计不涨、绑定读不到。是"守卫的守卫"(misses 必须 >0)暴露的
2. **`setExperimental('key', true)` 是 no-op** —— 它收**补丁对象**。四种 flag 组合的复现
   结果因此完全一样,我差点据此否掉整条真缺陷
3. **测错了路径** —— 我第一版路由测试驱动的是"抛出错误",而真实调用点在流式 translator
   的 `error()` 里处理 error chunk。12 条全红,但红的原因与契约无关

**共同判别动作**:每个复现/突变结果都要能回答"这个数字是怎么产生的"。答不出就是 harness
在骗你。

### 6.4 注释声称承重时,要问"经由哪个调用者才承重"

本轮两次:

- `forgetCloudModelCatalog` 内部的顺序只在**直接调用**时承重,经由 `removeAccount` 时上游
  已经先丢了目录 → 顺序无关。我的注释声称它承重,而突变验证显示零测试失败
- `messages.js` 的 `!messageStarted` 条件**不承重**(`startMessage()` 自己有 early-return,
  且 `this.model` 只被读一次)。承重的等价物在 `gemini.js`,那里每一帧都重读

**动作**:写下"顺序/条件很重要"时,立刻问"经由哪个调用者时它才重要",然后给那条路径
写测试。否则注释就是一句没有守卫的断言。

### 6.5 复现失败要归因,不能当成"缺陷不存在"

第一次复现 MODELS 泄漏得到 `delta +0`,看起来像"没这个缺陷"。真实原因是单条目快照被缩水
确认守卫隔离、`applyCloudModels` 压根没执行。**一次没能复现,和一次证明缺陷不存在,不是
同一件事。**

同一形态:散射断言原本归因于 issue #37,但移除那个比较器后测试仍全绿 —— 成因在候选**过滤**
(RPM 预留让刚服务过的账号对下一次不合格),我没隔离出来。已把断言消息改成钉结果而不是
机制。
