### 3.1 ✅ 已修(v3.9.8) 干旱判定会被单个账号触发

`auth.js:148` 的 `isDroughtMode()` 把没有配额数据的账号从**分母**里剔掉,
`droughtCount === knownCount` 于是变成"所有**有数据的**账号都干旱"。而
`refreshCredits` 失败时写的是 `credits = { lastError, fetchedAt }`(无 `weeklyPercent`),
正是上一份交接记过的"GetUserStatus 报 subscription has been canceled 而 chat 正常"
那个形态。

实测 40 账号池:

```
1 dry + 39 refresh-failed              drought=true   ← 1/40 就把整池限制到免费模型
1 dry + 1 healthy + 38 refresh-failed  drought=false
40 refresh-failed (none known)         drought=false
40 dry (真池级干旱)                     drought=true
```

触发条件精确:**≥1 个已知干旱 + 0 个已知健康**。一个刷新成功的健康账号就能压住。

另有观测口径不一致:`getDroughtSummary` 报 `knownAccounts=40`(Dashboard 横幅显示这个),
`isDroughtMode` 内部数的是 `1`。同一个词两个含义。

**这是潜伏缺陷** —— 干旱门禁在 connect 上从没跑过(见 3.2),所以它一直被掩盖;把门禁
接上的那一刻它变成用户可见故障。**修 #234 必须连它一起修,否则修复本身制造事故。**

修法方向:干旱判定要求最低已知覆盖率(而不是拿 1 个样本断言 40 个账号的状态),
`getDroughtSummary` 把两个 known 口径分开报。

### 3.2 ✅ 已修(v3.9.8) #234:干旱门禁在生产默认后端结构性不可达

`chat.js:2590–3366` 的 connect 短路块(锚点:`selectBackend({ modelInfo }).flow === 'devin_connect'`)**每条出口都 return**(逐字符核过大括号:流式
分支返回流式响应对象、非流式失败转移循环每个分支都 return、循环内无 depth-1 的
`break`),而干旱门禁在 `chat.js:3683`(锚点:`isModelBlockedByDrought(routingModelKey)`)。生产默认 `DEVIN_CONNECT=1`,所以它一次都没执行过。

**同一个结构原因还漏了 special-agent**:`special_agent` 分支在 `chat.js:3397`(锚点:`backendSel.flow === 'special_agent'`),也在门禁之上。
但 F1/F2 是**配置互斥**的 —— `DEVIN_CONNECT=1` 时 special_agent 分支本身不可达
(connect 优先级最高,5 个 special_agent 模型全解析成 `devin_connect`)。

**第三个逃逸点**:ACP vision 重路由(`chat.js:2597`,锚点:`acpVisionEnabled() && hasMultimodalContent`)在 strict-model 校验、entitlement
403、以及门禁的计划落点**全部之前**就 return 了。它不是 `selectBackend` 的 flow,是
`devin_connect` **内部**逃到 `special_agent` —— 所以按 flow 枚举的元守卫抓不到它。
**元守卫必须按逃逸点枚举,不能按 flow。**

### 3.3 ✅ 已修(v3.9.8) 干旱谓词跨了命名空间

`isModelBlockedByDrought` 用 `getTierModels('free')`(MODELS 空间)判 connect selector。
实测(当前 HEAD 仍如此):

```
isModelBlockedByDrought('swe-1-6-slow')     = true   ← connect 唯一免费可达
isModelBlockedByDrought('gemini-2.5-flash') = false  ← connect 根本路由不到
isModelBlockedByDrought('TOTAL-GARBAGE')    = true   ← 它是"不在免费表里"而非"是付费"
```

两个空间不相交(20 个 selector 是 MODELS key,但没有一个在免费表里,所以不存在意外正确)。
把门禁接上并复用这个谓词的结果是:**干旱时唯一还能跑的模型被屏蔽,而放行的那个跑不了。**

修法:新增 `isConnectSelectorBlockedByDrought(selector)` 走 `FREE_REACHABLE_SELECTORS`
(`auth.js:34` 已导入)。**不要复用也不要给旧谓词加参数** —— 两个空间就该是两个谓词。

**注意**:给它写"空集 fail-open"是**死代码** —— `FREE_REACHABLE_SELECTORS` 是模块级
冻结字面量,全仓无 `.add/.delete/.clear`。为它写测试会得到一条假测试。

`getDroughtSummary().freeTierModels` 要按后端解析,且**必须走 `getBackendSwitch` 而不是
`process.env.DEVIN_CONNECT`** —— Dashboard 可以在 env 未设时热切换 devinConnect(实测
env 删掉后 rows 130→56)。另注意 `getDroughtSummary` 是 arity 0 而 `handleModels` 收
per-request env,所以"四个面一致"不是结构性保证的,要显式钉。

### 3.7 #236:GLM 工具调用停滞 —— 诊断有结论,修法待定

两条猜测都被推翻:

- **不是"GLM 不支持工具"**:模型输出带 markup 时 `finish=tool_calls` 正常,链路是通的
- **不是 selector 没登记**:`glm-5-2-none` / `-max` / `-1m` / `-none-1m` 全部
  `mapped=true`(走归一化后的目录存在性检查),不需要补别名

```
A 文本声明意图、无 markup  -> finish=stop        tool_calls=0   (停滞)
B 文本带 markup            -> finish=tool_calls  tool_calls=1   (正常)
C reasoning-only           -> rescue 触发并愈合                (#238 已覆盖)
```

与 #238 同族,但 rescue 的条件是 `sawReasoning && !sawText`,**覆盖不到 A**。要不要也救
这一支需要真实上游复现后再定 —— A 的判据比 #238 模糊得多,容易把"模型真的只想用文字
回答"误判成失败。已在 issue 上请报告者用 OpenCode 直连复现并给两个具体信息。

## 5. 这一轮新增的方法论

上一份交接的 §5 仍然有效。这里只补它没有的。

### 5.1 对抗复核必须在**合并前**跑

上一轮是发版后跑,于是 v3.9.2–v3.9.6 每个版本都在修上一个版本。本轮改成合并前跑,
结果在**自己这一轮的修复上**找出 6 条(含 1 blocker)。同样的成本,换掉了一整个补丁版本。

### 5.2 "把 bug 固化成契约"的作者最可能是几小时前的自己

本轮出现 **4 次**:两条我写的断言编码了我刚修掉的缺陷,两条既有断言编码了别人的缺陷。
判别动作:**修完一个缺陷后,去看有没有测试在断言那个缺陷的现象。** 如果有,它的注释里
八成写着"the documented contract"之类的话。

### 5.3 结构守卫必须先剥注释

我自己写的目录守卫第一版**被自己的注释满足** —— 正则匹配到注释里引用的
`applyCloudModels([])`。与复核在同族守卫上查出的"注释满足断言"是同一个反模式。

### 5.4 守卫的词汇表会漏掉整个家族,而且会漏第二次

`connect-error-blame` 的演进史:UPPER_SNAKE 字面量 → 加 socket 码 → 加透传的小写 gRPC
status → 放宽字符类到含数字与连字符。**每一次都以为已经完整了。** 判别动作:问"这个
词汇表是从哪里推导的?那个来源会不会本身就不完整?" —— 透传(`code: code || 'X'`)
按构造就是开放的,任何从源码字面量推导的词汇表都看不见它。

### 5.5 注释里的论据也要验

我写"RETRYABLE_CODES 已把这些当可重试",复核实测 `isRetryable` 对那三个 gRPC status
全是 `false` —— 论据只对 socket 码成立。**"注释不是事实"这条,对自己刚写的注释同样适用。**

### 5.6 一条断言可能同时耦合两个维度

`rate-limit.test.js:120` 既断言精确毫秒、又隐含断言"走的是哪条分支"。注入 4.5 秒延迟后
另一条分支回答约 1622996ms,而原断言把它当成"大约 1632000"照样通过 —— **测试在走错代码
路径时仍然全绿**。修的时候两个维度都要显式钉。

### 5.7 操作纪律补两条

- **批处理命令容易让 shell 卡住**,拆细逐条跑更稳。本轮卡过两次,第一次我误判成"CPU
  被忙等进程占满"(实际 `pgrep` 无残留、磁盘 70Gi 空闲)—— **不要猜原因**
- **终端渲染会截断**:`git log --oneline -3` 只印一行。权威读数用 `.git/logs/HEAD`
- **本机 shell 是 zsh,不是 bash。** 两个 bash 习惯会静默失效,而且**失败长得和"守卫是
  瞎的"一模一样**:
  - `TESTS="a.js b.js"; node --test $TESTS` —— zsh 不对未加引号的变量做词分裂,两个路径
    作为**一个**参数传进去,node 报 `Could not find 'a.js b.js'`。用 `${=TESTS}` 或数组
  - `read A B < <(cmd)` —— 进程替换配 `read` 读不到值,变量留空
  
  接手时的判别动作:**突变验证必须先看 baseline 的 pass 数**。我这轮连拿 4 次
  "SURVIVED — 守卫是瞎的",全部是 `pass=0` —— harness 一个测试都没跑。
  `pass=0 fail=0` 不是"守卫没抓到",是"没测量"。**先证明 baseline 非零,再相信任何
  SURVIVED 结论。**(与台账里"confirmed:0 常是没跑成"同一条)
